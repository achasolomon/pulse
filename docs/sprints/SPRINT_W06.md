## First laboratory order

The treating clinician can open **Order laboratory test** from the current encounter, investigation summary or **Patient → Investigations**. The desktop side drawer/mobile bottom sheet shows patient identity and eligible encounter, searches the selected facility's available catalogue by name/code, displays the specimen requirement and records urgency/clinical indication. A final review shows the exact selected test/version, encounter and indication and requires an explicit review attestation before placing the request. No order is created during selection/review. Failed requests, stale catalogue selections and unsaved changes retain the authored information.

Orders pin the selected test ID and catalogue version and attribute the authenticated ordering clinician and time. The history refreshes after placement; **Review laboratory order** shows status, original indication, catalogue/specimen details and author. **Review cancellation → Confirm cancellation** records a reason, actor and time while retaining the original request. This action is allowed only while ordered, before any specimen/result exists. Processing/verification/release are separate workflows; placing an order does not imply collection, a result, patient notification or laboratory acknowledgment.

Migration 0043 adds facility test availability and order attribution/revision fields. Catalogue selection is restricted to active, approved test versions at that facility; when more than one active version is approved, the latest is offered. Historical order details remain pinned. The server rechecks availability/version at placement. Same-test pending duplicates in the same encounter require review rather than a silent repeat or override. One test per request is the deliberate first slice; repeat/add-on and override governance remain pending.

Staff routes require selected organization/facility, patient care, laboratory read plus the action capability, an active encounter-specific care assignment and treating-clinician consultation capability. Outpatients require ownership of an in-consultation visit. Reads validate patient/encounter/facility consistency and current care. Writes lock encounter/care/ownership; actor-scoped command receipts and encounter serialization prevent duplicate retries/competing submissions. Cancellation checks the current revision/state and specimen/results under an order lock. Order state, metadata-only audit, receipts and outbox commit atomically, using the existing laboratory event producer. Indication and cancellation narratives are not copied into receipts/events/audit metadata. Legacy demo adapters remain available under their existing gated auth; all legacy laboratory routes reject staff sessions so they cannot bypass scope/attribution.

Migration 0044 serializes specimen/result insertions with cancellation and prevents new specimens/results or status resurrection after cancellation, including delayed legacy adapter calls. This does not introduce a collection or reporting UI.

The opt-in `scripts/seed-local-lab-catalogue.mjs` supplies explicitly labelled Demo Full blood count and Demo Urinalysis entries only at the two local role-demo facilities and enables local demo doctor/admin order/cancel capabilities. Their specimen text is explicitly a preview placeholder requiring approved configuration before clinical use. No orders, results or patient clinical records are created by this seed. The patient preview seed also retains the local capability mapping.

## Laboratory duty queue and specimen workflow

**Staff worklists → Laboratory** is available with `patient:read`, `lab:read` and `lab:worklist`. Duty access is through the facility's valid laboratory service orders, not an unrestricted patient care assignment. Staff can review necessary order, patient identity and specimen details; this capability does not grant access to the wider chart. Sidebar, workspace and general worklist search entry points expose the work area for laboratory-only accounts.

The queue includes all pending orders (ordered/collected/accessioned/resulted), with explicit stage filters and counts, prefix patient/test search or exact identifier, urgency then oldest-first ordering, complete matching counts/oldest age and cursor pagination (25 per page). Age is time since ordering; no unapproved overdue threshold is inferred. It refreshes every 20 seconds while active, pausing periodic refresh during specimen entry. Invalid/foreign/inconsistent order-patient-encounter links are excluded. Counts cover the complete matching queue, not only the displayed page.

**Review request → Review collection → Confirm collection** records the actual container, physical specimen identifier, actual time, authenticated collector and explicit patient/label confirmation. Collection requires `lab:collect`, active patient/encounter, current revision, ordered state and no prior specimen/result. It moves the request to awaiting receipt. Manual label entry is supported; barcode printing/scanning hardware validation is not implied.

**Review request → Review receipt → Confirm accession** requires `lab:accession`, the matching single collected specimen, an accession identifier, actual receipt time and explicit identity/suitability confirmation. It attributes the receiving staff and advances the request to accessioned/ready for testing. Already collected specimens may be received after encounter closure; new collection after closure is blocked. Retired patient identities, inconsistent/multiple legacy specimens and conflicting identifiers require governed reconciliation instead of an arbitrary choice. This slice accepts suitable specimens; rejection, conditional acceptance, recollection, additional aliquots and correction workflows remain pending.

Migrations 0045–0046 add collector/identity evidence, facility-scoped specimen-label identity and accession records, uniqueness guards and protection against overwriting recorded custody facts. Legacy rows keep unrecorded attribution/identity fields rather than fabricated confirmations. No specimen label is automatically generated or silently reassigned. Revisions, order/identity locks and actor-scoped receipts guard concurrent/retried work. Actual times must follow the order/collection event and cannot materially exceed current time. Clinical chart investigation history exposes collection and receipt evidence through existing care-scoped laboratory reads. Durable laboratory events/audit/receipts commit with the transition and exclude label, container and indication text.

The opt-in local catalogue seed now enables the existing `demo.lab` account at its existing demo facility with duty read/collect/accession capabilities, without adding care assignments. It uses the existing generated local demo password. No patient orders/specimens are created in the normal database by enabling the account. Department/bench assignment, phlebotomy access for treating nurses, specimen rejection/recollection/custody corrections, label printing, instrument/result entry, verification, accountable clinical routing and production clinical acceptance remain pending.

## Manual results and independent verification

**Staff worklists → Laboratory → Review request** now offers result capture for accessioned requests with `lab:result`. Manual bench entry records component, value, optional unit, explicitly supplied interpretation (unset by default), actual measurement time and authenticated author. Entry requires a source/identity attestation and a component review before saving. Revising a component appends an attributed revision and preserves prior values; case-only spelling changes retain the existing component identity. Draft findings are visible only to laboratory result/verification capabilities and remain absent from the patient chart. The queue does not include result narratives.

`lab:verify` is a separate capability. A different authorised verifier reviews all current components and explicitly attests to panel completeness, identity, units, interpretation and required facility checks before publishing. Stale order revisions, missing provenance, empty reports, inactive identities and self-verification are rejected. Verification and its metadata-only audit/outbox evidence commit together; clinical chart reads expose only the latest verified component versions. Final component entry/overwrites are blocked. Migration 0047 adds manual provenance and database revision protection. No API to delete results or silently reopen final reports is provided.

Critical findings have a prominent warning and cannot be finalised through this slice: accountable notification, named recipients, attempts, acknowledgement and escalation are not yet implemented. The UI directs authorised staff to their facility's direct escalation procedure. This is a development workflow, not a complete clinical release implementation. Result entry does not automatically assign normality, calculate reference ranges, validate panel completeness, enforce analyser/QC policy or create clinician review acknowledgement. Approved component catalogues/reference intervals, facility validation configuration, analyser/LIS import, corrected/amended reports, accountable clinical routing and production acceptance remain required.

The opt-in local catalogue seed enables `demo.lab` result entry and `demo.admin` independent verification for local review only; existing passwords are unchanged. These demo permissions are not production role policy. No orders/results or new care assignments are seeded. Use the same facility for author and verifier.

## Critical communication and acknowledgement (2026-10-22)

The earlier blanket critical-release hold is superseded for the controlled manual-bench path only. A separate `lab:verify` laboratory professional confirms the critical finding and assigns a named clinician with active facility membership, `patient:read`, `lab:read`, `lab:critical:ack` and current patient care responsibility. A follow-up deadline is explicitly chosen under facility policy; Pulse does not invent a clinical SLA. Confirmation pins the complete current report revision. Result edits are then blocked pending a governed correction workflow.

Laboratory staff record actual phone/in-person contact attempts. Unreachable attempts stay unresolved. A reached attempt requires explicit read-back confirmation; contact evidence is attributed, retained and protected from overwrite. A named recipient must separately review the confirmed finding and explicitly acknowledge responsibility. Viewing, polling, notification counts, contact attempts and read-back do not acknowledge the finding. Acknowledgement does not complete treatment or publish a report. Final laboratory verification remains a separate authenticated, independent action and requires acknowledgement of the pinned report before critical release. Verified chart investigation history retains acknowledgement attribution/time; unreleased result values remain withheld from the ordinary chart.

The persistent **Critical follow-up** header indicator opens `/critical-results`, with a pending worklist, visible deadlines/past-due indicators, patient identity, confirmed findings and contact/acknowledgement evidence in desktop side/mobile bottom drawers. Counts contain no patient data. Clients poll every 15 seconds while active; this is an authenticated in-app worklist, not guaranteed Web Push or an external transport. It is deliberately distinct from the ordinary inbox read/unread bell. Failed refreshes show unavailable, not zero. Cases persist after encounter closure, and withdrawing a recipient's care access blocks their detail/acknowledgement while laboratory duty users retain the unresolved case. ## Configured backup activation and immediate cover

Migration 0050 adds immutable backup-routing records and recipient-specific contact evidence. Existing contact rows are attributed to the original named clinician, matching the earlier workflow's explicit communication attestation. The original case recipient is never overwritten. An authorised laboratory verifier can add a covering clinician immediately or configure activation at the case's existing follow-up deadline. Selection requires current membership, active credentials, acknowledgement permission and current patient care responsibility. A reason and explicit review/attestation are required. Scheduling does not grant care access or expose the finding to the backup before activation.

The in-API escalation worker checks durable scheduled rows every five seconds, including on startup. Concurrent workers serialize through the laboratory order/case locks; decisions, case revisions, metadata-only audit and outbox evidence commit together. Activation rechecks the recipient's credentials, membership and care access. A withdrawn/ineligible recipient produces a visible **blocked** record; the original case remains unresolved and laboratory staff must escalate directly or add another eligible clinician. Worker errors preserve scheduled work for retry. This is per-case configured routing against the existing deadline, not an inferred SLA or a facility-wide policy engine.

Active covering clinicians receive the same persistent pending header/worklist access as the original clinician, subject to current care permissions. Contact attempts identify the actual named recipient. A primary recipient's read-back cannot authorise a backup's acknowledgement: the covering clinician needs their own reached/read-back evidence and explicit acceptance. The first valid acknowledgement closes the communication case; competing acknowledgements cannot overwrite it. Scheduled backups are cancelled when acknowledgement occurs first. Final report release remains a separate laboratory action. Original assignments, routing reasons, failed attempts, activation decisions and actual acknowledgement attribution remain retained.

The **Cover & escalation → Add covering clinician** panel provides immediate/deadline options, review and failure retention inside the existing desktop/mobile drawers. Dirty state and busy state are combined across result entry, contact and routing controls. The browser review found an Escape timing issue in this nested state propagation; dirty state now propagates immediately as well as remaining synchronised across child forms.

## Initial imaging requests and cancellation

Migration 0051 adds a versioned, facility-mapped imaging catalogue and attributed commands. **Patient → Investigations → Request imaging** opens the desktop side drawer/mobile bottom sheet. The treating clinician selects an available procedure, records side, urgency, indication and optional relevant safety context, then explicitly reviews and attests before submission. Body region, modality and catalogue version come from the server. Required and non-applicable sides are enforced. Failed requests retain authored information; retries are deduplicated and duplicate pending requests are rejected.

Ordering and reasoned early cancellation require current facility membership, patient care access, consultation permission and the assigned active encounter. Cancellation checks the revision and rejects requests once scheduling/processing, a study or a report exists. Cancelled requests remain in history and cannot acquire a study/report. Audit/outbox records contain metadata rather than clinical narratives. Unmapped legacy requests remain readable without invented catalogue provenance. Staff cannot bypass the workflow through the legacy imaging adapter.
